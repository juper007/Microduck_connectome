## Required verdicts

| Field | Decision |
| --- | --- |
| `ROBOTD_ACK_SEMANTICS` | `robot.move` request parsed, twist stored in `Intents`, then an `accepted` response is written. ACK proves acceptance and storage of an intent value; it does **not** prove a control tick consumed it, safety passed it, a motor write succeeded, or the body moved. |
| `STATE_TIMESTAMP_SEMANTICS` | `robot.state.t_ns` is `CLOCK_MONOTONIC` at the tick's successful **sensor read**, before the intent snapshot, safety gate, policy step, motor write, frame assembly, broadcast, and socket delivery. A coasted tick reuses the previous successful sensor-read timestamp. It is not a state-generation or command-consumption timestamp. `robot.state.t` is daemon-relative elapsed seconds. |
| `SOURCE_CLOCK_COMPARABLE` | `PARTIALLY`: pinned robotd uses Linux `CLOCK_MONOTONIC`; CPython 3.12 `time.monotonic_ns()` uses its platform monotonic clock. Numeric comparison on Thor is legal only after a recorded runtime check that Python's implementation is `clock_gettime(CLOCK_MONOTONIC)` (or equivalent bracketed comparison with `time.clock_gettime_ns(time.CLOCK_MONOTONIC)`) on the **same host**. Even then, comparing `t_ns` to an ACK orders the sensor read, not the intent snapshot or exact command generation. `t_ns=0` and repeated coast timestamps cannot prove freshness. Cross-host or Windows comparisons are invalid. |
| `COMMAND_VISIBILITY_RULE` | Existing `state.move.requested` is the twist value read by one control-loop `Intents::snapshot()`. Equality with a sent velocity shows a value match, **not which writer/request supplied it**. A future exact rule requires `state.consumed_move_generation == ACK.accepted_move_generation`. |
| `COMMAND_APPLICATION_RULE` | `state.move.applied` is the same tick's gated and slewed policy command, and `limited_by` includes deadman/safety limits from that tick. A future exact command attribution requires the matching consumed generation, positive applied vx at the frozen minimum, and no deadman/fault/safety limiter. The ACK alone never proves application. |
| `PHYSICAL_MOVEMENT_RULE` | Use independent, fresh MuJoCo body-pose samples for the frozen 0.01 m displacement and 0.015 m/s for 200 ms speed requirements; require the fresh, attributed applied vx immediately before arm. State fields alone do not prove body movement. |
| `DEADMAN_SCOPE` | `CAUSAL_POST_COMMAND_WINDOW`, **prospective only**: the window begins with the first completely observed state proven to have consumed an accepted positive move generation. A deadman/fault/safety state at that first tick or any later tick through arm fails; later clean motion cannot erase it. Earlier states proven to consume an older generation are retained as acquisition transients and cannot qualify. Missing state/tick continuity or unresolved lineage fails closed. PR #93's current all-acquisition disqualification remains active until a separate reviewed implementation changes it. |
| `SELECTED_OPTION` | `B` |
| `METADATA_CHANGE_REQUIRED` | `YES` |
| `HISTORICAL_TPR2A001_STATUS` | `UNCHANGED_UNRESOLVED_FAIL` |

The prospective deadman scope follows the scientific moving-body question:
a tick proven to have consumed an older, pre-move intent is not evidence of
the commanded moving body, while the **first** tick proven to consume an
accepted positive move is evidence and must be judged, including if it is
deadman-limited. The original helper already distinguishes initial readback
from a post-motion state, but PR #93 deliberately enforces all-acquisition
contamination while causality is unresolved. A later implementation may adopt
this narrower *causally defined* start only after science/safety review. It
must still supply at least the frozen 1.5 s of 20 ms commands **from that
start** (extending acquisition if needed), keep every state in the raw record,
and fail on any causally post-command deadman/fault through arm. Thus neither
the duration nor the no-deadman requirement is relaxed.

The precise ordering around an ACK can be `sensor read → old intent snapshot/frame → move store → ACK → old frame delivery`, or `sensor read → move store → new intent snapshot/frame → ACK → frame delivery`. Both are compatible with a state `t_ns` before ACK and host receipt after ACK. A timestamp after ACK, with verified clocks, proves that sensor read preceded a later snapshot after ACK, but without a command generation it cannot identify which of potentially competing twist writes that snapshot consumed. A matching requested velocity can be produced by an older or another identical writer. No `robot.state` field currently carries a control-tick identity or consumed request/generation.

## Minimal diagnostic metadata contract for a separate task

This is an additive **observation contract**, with no change to intent values, safety gate, control cadence, motor authority, or behavioral thresholds.

1. Give every twist mutation (`robot.move` request or notification, `robot.stop`, and every other twist-setting path) one process-wide, strictly increasing `move_generation`. Allocate and publish the generation **with** its twist value as one linearizable operation, so concurrent writers cannot publish generations out of order. Do not use JSON-RPC `id` as a global command identity; it is client-local.
2. A request-form `robot.move` accepted response includes `accepted_move_generation=N`, the exact generation published by that request. ACK still means accepted/stored only. A rejected request has no accepted generation.
3. Each control-loop tick receives a strictly increasing `control_tick_sequence`, even if no state frame is published. The single `Intents::snapshot()` for that tick returns the twist and its generation together. Every published `robot.state` includes `control_tick_sequence` and `consumed_move_generation`, the generation used for its `move.requested`, `move.applied`, limiter and policy calculation. Keep existing `t_ns` semantics unchanged. A coasted sensor read retains old `t_ns` but has a new tick sequence.
4. Preserve a complete, non-decimated diagnostic subscription from before the first move through arm. Fail closed on a tick-sequence gap, state parse error, stream lag/reconnect, non-monotonic generation, source timestamp regression, or unverified clock/freshness. The diagnostic task must adjust the client subscription once, rather than reissuing `robot.subscribe` for every notification. It must durably retain every delivered state, ACK generation and raw request lineage. No evidence claim of continuity may be made if robotd did not publish a tick due to missing sensors.

`CAUSAL_STATE_RULE`: for accepted positive move generation `N`, a state is attributable to that exact command only when its coherent tick frame reports `consumed_move_generation == N`, its tick sequence is strictly newer than the pre-move state, the diagnostic stream is contiguous, and the state is fresh. A generation `< N` is pre-command for that request; a generation `> N` means it was superseded and cannot be attributed to `N`. The first state consuming any accepted positive move generation begins the prospective causal moving window. A deadman/fault/safety limiter in that first state or any later state before arm is terminal for that acquisition. A clean state cannot erase it. `requested`/`applied`, policy, health, and independently measured pose must then satisfy the unchanged frozen gate.

The metadata resolves *which intent the tick consumed*. It does not prove the motor bus physically executed its targets; physical movement continues to require measured simulator pose. Consecutive same-valued moves have distinct generations. If one is superseded before a tick, there is no state attributable to it; this is a valid observation, not a fabricated success.
